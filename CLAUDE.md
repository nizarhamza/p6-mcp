# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

P6 MCP: a local MCP server for **Primavera P6 Professional standalone (SQLite)** databases, packaged as a
Windows product (server exe + Settings/tray app, installer, GitHub releases). Not affiliated with Oracle.
Python 3.10+ (3.13 locally), FastMCP from the `mcp` SDK (1.8+ or 2.x shim).

**Never commit real project data**: no .db, .xer, logs, backups, screenshots or client names. Tests use the
synthetic database built by `tests/fixtures/make_db.py`. Real-data regression tests (CPM against P6's F9)
stay outside this repository.

## Layout

- `p6mcp/server.py`: the server (the former single-file `p6_mcp_server.py`, 46 tools). Entry point
  `python -m p6mcp` (`p6mcp/__main__.py`).
- `p6mcp/config.py`: `%APPDATA%\P6MCP\config.json` (`P6MCP_CONFIG` overrides), `schema_version` + `MIGRATIONS`,
  `validate`, atomic `save` (temp file + `os.replace`, `.bak` kept), `load()` -> frozen `Settings` (cached on
  mtime/size; never raises: `config_error`, `db_problem`). Env vars win (`P6_DB_PATH` = explicit selection,
  `P6MCP_TOOL_PROFILE`, `P6MCP_ALLOW_WRITES`...). P6_DB_PATH without a config file keeps the v2 layout
  (files beside the DB, backup once per process, no pruning). A database entry is used only when
  `confirmed` (set by `confirm_database` after Test connection). Secrets are refused in the file.
- `p6mcp/credentials.py`: Windows Credential Manager via keyring (service `P6MCP`, `P6MCP_SECRET_SERVICE`
  for tests): `http_token`, `db:<profile>`.
- `p6mcp/policy.py`: `TOOL_KIND` (read / file / write / destructive) for every tool, `BASIC_TOOLS`,
  `listed()` (tool list fixed at startup), `refusal()` / `write_refusal()` (checked on every call).
- `p6mcp/schema.py`: schema fingerprint (SHA-256 of table.column names), `KNOWN_SCHEMAS`, P6 version from
  `PREFER.database_version`; unknown schema = read only unless the user trusts it (`trusted_schemas`).
- `p6mcp/confirm.py`: `TokenStore` (in process, 15 min, single use, bound to tool + canonical arguments +
  database + plan digest).

- `p6mcp/dbcheck.py`: `suggestions()` (SQLite connections of P6's `PrmBootStrapV2.xml` under
  `%APPDATA%`/`%LOCALAPPDATA%\Oracle\Primavera P6\P6 Professional\<version>`, newest first, then
  `Documents\PPMDBSQLite.db`; suggestions only, never selected) and `test_connection(path, trusted)` (read only:
  schema, P6 version, project / EPS / baseline counts, `writes_possible`, `warnings`).
- `p6mcp/settings_logic.py`: config edits without Qt (add / update / remove / set_active / confirm a database,
  `trust_schema`, `port_free`, `restart_needed` on `RESTART_KEYS`, `tool_rows`, broken file set aside). A new
  path clears the confirmation; `confirm` needs an ok test of the same file.
- `p6mcp/i18n.py` + `p6mcp/locales/<lang>.json`: `tr(key, **fmt)`, en is the reference and fallback, `auto` =
  Windows display language, `is_rtl()` mirrors the layout (Arabic only needs its catalog). Strings: straight
  quotes, no long dashes (test). Every key used by the UI must exist in en.json and every catalog must have the
  same keys and placeholders (`tests/test_i18n.py`).
- `p6mcp/settings_app/`: PySide6 Settings window (`python -m p6mcp.settings_app`, `p6mcp-settings`):
  `window.SettingsWindow` edits `self.data` (config dict) and writes only on Save (`config.save`); pages
  `DatabasePage` (test runs on the thread pool through `common.Job`), `ServerPage` (transport, port check,
  token in the Credential Manager), `ToolsPage` (profile, writes with confirmation dialogs, backups, tool list).
  Dialogs go through `common.ask` and `SettingsWindow.ask_close` so tests can answer them. HiDPI: PassThrough
  rounding, layouts only (no fixed pixel sizes except font-metric based ones).

- `p6mcp/jsonc.py`: parser with spans (comments, trailing commas, BOM-free text) and minimal edits
  `set_member(text, path, key, value)` / `delete_member`: only our member's text changes (indentation, line
  endings and comments of the file followed), and every edit is re-parsed and compared with the expected
  value before it is returned (`JsoncError` otherwise). An add then a delete gives back the original bytes,
  except a trailing comma before our entry and the empty containers an add created.
- `p6mcp/clients/`: one `Adapter` per client in `adapters.py` (`ADAPTERS`: Claude Desktop, Cursor, VS Code,
  VS Code Insiders, LM Studio, Cline; paths and formats checked against each client's docs, sources in the
  module docstring). An adapter declares `config_path()`, `installed()`, `container` and `stdio_entry()`;
  `base.Adapter` does `status()` (not_installed / not_registered / registered / outdated / error, `others` =
  other P6 MCP entries such as the v2 `primavera-p6`, `running`), `register()` (add or repair) and
  `unregister(key)` (a foreign key only when it is a P6 entry). Every write: parse first (a malformed or
  non-UTF-8 file is refused and untouched), backup in `%LOCALAPPDATA%\P6MCP\client_backups\<client>` (20 kept),
  minimal edit, `files.write_atomic` (temp + `os.replace`, retried, BOM kept). `base.launch()`: frozen ->
  `p6mcp-server.exe` beside the running exe, else `python.exe -m p6mcp`. Registration writes stdio entries;
  HTTP entries come with the HTTP host (milestone 4); `clients.snippet()` gives stdio, HTTP and VS Code text.
  CLI for the installer: `p6mcp-server clients list|register|unregister|snippet` (`--detected`).
- Settings `ClientsPage` (`clients_page.py`): scan at every launch (thread pool), Register / Repair / Remove /
  remove a v2 entry / Do not offer again (`clients_ignored`, saved with Save), snippets. The window banner
  offers new clients and flags entries to repair (after the no-database warning).

## Server gate and two-step writes (milestone 1)

- `_refresh()` re-reads the settings at the start of every client call (module globals `DB_PATH`, `P6_USER`,
  `BACKUP_DIR`, `LOG_DIR`, `SKIP_PROC` follow; a new database clears `_cols_cache`, `_schema_cache`, the
  backup state). `STARTUP` = settings the tool list was built with; `p6_diagnose` reports `restart_required`.
- `_tool` stores `REGISTERED[name] = _gated(fn)` (what clients reach) and registers it with the SDK only when
  `policy.listed`. `_before_call` refuses per policy and, except `NO_DB_TOOLS`, without a usable database
  (`config.NO_DB_MESSAGE`). The plain module functions stay callable directly (tests, internal use) and keep
  `confirm=True` semantics without tokens; the settings and schema gate (`_write_refusal`) is in the write
  path itself (`_open_for_write`, `p6_restore_backup`, `p6_backup_database`), so it applies to direct calls too.
- Write tools get `dry_run` (default true), `confirmation_token` and, for destructive ones, `confirmation_text`
  (`_confirm_text`: `DELETE PROJECT <ids>`, `DELETE ACTIVITY <project> <code>`, `RESTORE <name>`); `confirm`
  stays as a deprecated alias that still needs the token. The SDK reads `__signature__` without evaluating
  strings: `_gated` builds it from `inspect.signature(fn, eval_str=True)`.
- `_CALL` (contextvar) carries the call: `_plan_gate(plan, confirm)` in `_commit` (and restore) records the
  dry-run plan digest (lines starting `Backup: ` ignored) and refuses an apply whose rebuilt plan differs.
  A token is consumed when the change is applied or the plan differs; a refusal that writes nothing
  (`applied: False`, P6 running) keeps it. A dry run with `would_refuse` gets no token. `_log_write` adds
  `params` and `confirmation` (token prefix) to edit log entries; `_log_dirs` also reads the v2 folder beside
  the database.
- `p6_sql_select`: `_sql_authorizer` (SELECT, READ, FUNCTION, RECURSIVE, read-only PRAGMAs in `SQL_PRAGMAS`),
  `SQL_QUERY_SECONDS` progress handler; `PRAGMA query_only` on every read connection. `p6_export_xer`
  refuses an existing file without `overwrite=True` and the database path.
- `INSTRUCTIONS` must stay ASCII and under 1 KB (974 B now).

## Architecture and invariants

- **P6 schema conventions**: tables are P6's own (`PROJECT`, `PROJWBS`, `TASK`, `TASKPRED`, `CALENDAR`, `NEXTKEY`). Durations, lags and float are stored in **hours**; the API exposes **days** by dividing by the activity calendar's `CALENDAR.day_hr_cnt` (use `HPD_SQL` in queries: 0 or NULL falls back to 8). Lag days (read and write) use `_lag_hpd`: the project schedule option `sched_calendar_on_relationship_lag` from PROJPROP prop_name='scheduling' (rcal_Predecessor, rcal_Successor, rcal_24Hour = 24 h, rcal_ProjDefault = PROJECT.clndr_id), else the predecessor calendar (P6 default). The option of the successor's project applies to cross-project links. `_lag_rule(con, pid)` returns `(rule, source)`; `p6_get_relationships`, `p6_get_activity` and the add/update relationship plans report the rule used. Enum codes: `PR_FS/SS/FF/SF`, `TK_NotStart/Active/Complete`, `CS_*` constraints, `TT_*` task types (mapping dicts at top of file).
- **Schema tolerance**: columns vary between P6 versions, so code checks `_cols(table)` (cached `PRAGMA table_info`) before reading/writing optional columns, and `_alive()` appends `delete_session_id IS NULL` only when that column exists (P6 soft deletes). Preserve this pattern in new queries.
- **Row keys**: P6 column names are upper case, so `dict(row)` gives `TASK_NAME`. Use `_dict()` (lowercase keys) for anything returned to the caller; `sqlite3.Row` indexing itself is case-insensitive.
- **Relationships**: two activities may be linked once **per type** (SS + FF pairs are common). Identify a relationship by (pred, succ, type); `_find_rel` asks for `current_type` when a pair is ambiguous. Neither add nor update may create a second link of the same type on a pair (update refuses a type change onto a type that already links it). One link change is `_rel_add` / `_rel_update` / `_rel_delete` (`_rel_delete_row` for a TASKPRED row) on an open write connection, returning {plan, log, projects, ...}; `_Refused` (a ValueError) marks the refusals the single-link tools return as `{applied: False, error}` (`_single_link`). The batch tools (`p6_add_relationships`, `p6_update_relationships`, `p6_delete_relationships`: ids and pairs, at most `MAX_BATCH` items, item keys checked against `LINK_KEYS`) run them through `_link_batch` = `_batch` + `_batch_commit` (all or nothing) and return `side_effects` (`_side_effects`: open, non-summary activities that lost a predecessor or successor and have none left, summary links not counted, as the health check) and `lag_rule`. Deletes are hard deletes, as P6 and the GUI do.
- **Lookups by user-facing codes**: tools take `project` = `proj_short_name` and `task_code` (Activity ID), resolved via `_project_id` / `_task` (which also joins the calendar to get `hpd`).
- **Read path**: `_connect()` opens SQLite read-only via `?mode=ro` URI. Every list tool (`p6_list_projects`, `p6_list_eps`, `p6_list_wbs`, `p6_query_activities`, `p6_critical_path`, `p6_float_paths`, `p6_get_relationships`, `p6_list_calendars`, `p6_compare_projects`, `p6_lookahead`, `p6_group_summary`, `p6_resource_summary`, `p6_sql_select`) returns one page `{total, offset, returned, next_offset, rows}` plus tool-specific sibling keys (`root`, `lag_rule`, `project`, `definition`/`mode_used`/`threshold_h`/`counts`, `paths`/`source`, `summary`/`projects`, `window`/`data_date`, `code_filter`, `by`/`level`/`code_type`/`totals`, `schedule_state`, `note`); there is no `_note` row, and `next_offset` is None on the last page. Limits are clamped to `MAX_ROWS` (200); defaults are 50 for activity lists (look-ahead included) and calendars, 100 for WBS, relationships, group and resource summaries, 200 for projects, EPS and SQL. Paging helpers: `_check_page` (offset >= 0, limit 1 or more), `_env`, `_page(con, sql, args, offset, limit, row_fn)` (COUNT and page in one read snapshot; run sibling reads inside the same `BEGIN` when they must agree with the page) and `_slice` for lists built in Python. Never filter rows in Python after `_page` (the total would be wrong), and end every ORDER BY with an id tiebreaker (`t.task_id`, `wbs_id`, `task_pred_id`). `p6_sql_select` accepts one SELECT/WITH/PRAGMA table_info, strips trailing `;`, and skips `offset` rows in chunks of 1000, and counts only when a page is full, never for PRAGMA, at most `SQL_COUNT_CAP` rows and `SQL_COUNT_SECONDS` (progress handler); otherwise total is None plus a note. It also ends a page early (at least one row, a note, `next_offset` continues) once the estimated client JSON of its rows passes `SQL_PAGE_BYTES` (150,000), so a wide `SELECT *` stays under the 200 KB page budget. `p6_list_calendars(include_exceptions=True)` pages at most `CAL_EXC_ROWS` (50) calendars and lists at most `CAL_EXC_EACH` (100) exception dates per calendar and `CAL_EXC_PAGE` (800) per page (a running budget in the row function; `exception_dates_truncated` per row, a note when any is cut). `p6_get_activity` stays a dict: plain lists capped at `ACT_LINKS_CAP` (50) for predecessors/successors (with `predecessor_count`/`successor_count`), assignments (RSRC and ROLES), activity codes, UDFs (value column per `UDF_VALUE`) and notebooks (`_memo_text`: HTML stripped, 500 characters), plus `ACT_EXTRA` dates, calendar, `wbs_code`/`wbs_path`, `lag_rule` and `schedule_state`.
- **Activity rows**: `_act_from(con)` is the base SELECT of every activity list (TASK `t` + CALENDAR `c` for `hpd` + PROJWBS `w` for `wbs_name`, one `proj_id` parameter, `_alive` applied); append `AND` conditions and an ORDER BY. `_act_view` returns exactly the `ACT_FIELDS` keys (from the `ActField` Literal, None for a missing column; `ACT_HOURS` maps the day fields to their hour columns; `cstr_label` is `CSTR_LABELS[cstr_type]`, and `p6_get_activity` adds `cstr_label2`) and `_act_row(fields)` serves `fields=`: task_code first, duplicates ignored, unknown names raise before any SQL. A new row field goes into `ActField` (the test compares row keys with `ACT_FIELDS`).
- **WBS and critical path**: `_wbs_tree(con, pid)` walks PROJWBS from the `proj_node_flag='Y'` node (its parent is the EPS node) with a recursive CTE, in P6 order (siblings by `seq_num`, then `wbs_id`, fixed-width text sort key), giving `depth` and `wbs_code` (short names joined with `_name_sep`: PROJECT, then PREFER `name_sep_char`, else '.'). `p6_list_wbs` reads the tree, the per-WBS `_act_agg_sql` aggregates and the stored PROJWBS count in one `BEGIN`, filters by `parent`/`max_depth` in Python and rolls up bottom-up with `_merge_agg` (keys in `AGG_MIN`/`AGG_MAX` keep the extreme, the others add). In `_act_agg_sql`, open (and the float and negative float of open activities) is the analysis definition: not `TK_Complete` and not `SUMMARY_TYPES`. Units are labor plus nonlabor (`*_work_qty` + `*_equip_qty`); `_rollup` gives `units_pct` = actual / (actual + remaining), P6's Units % Complete. `_critical_clause(con, pid, mode, threshold_days)` returns `(sql, args, definition, threshold_h, mode_used)`: mode 'project' follows `PROJECT.critical_path_type` (CT_TotFloat: total float <= `critical_drtn_hr_cnt` hours; CT_DrivPath: `driving_path_flag='Y'`), `float_threshold_days` compares days of each activity's calendar. `p6_critical_path` never lists `SUMMARY_TYPES` (TT_LOE, TT_WBS), even when P6 flags them: its definition says so and `counts.excluded_summary` counts the ones that match. `p6_float_paths` reads `TASK.float_path`/`float_path_order` (P6 order, never re-sorted) and falls back to `driving_path_flag` without `SUMMARY_TYPES` when none is stored. `p6_list_projects` takes the status from the project WBS node (PROJECT has no `status_code`).
- **Health check additions**: `_dcma` also returns `items` = check -> (sql, args, row_fn, key_fn) in sample order (`act` with `HC_ACT_FIELDS` rows and optional flag columns, `rel` link rows with `task_pred_id`, missed_tasks); `check=` (`HcCheck` = DCMA 14 + key_dates; `HC_NO_ITEMS` refused) pages them with `_page` (key_dates with `_slice`) inside the same snapshot. `checks["key_dates"]` (after bei, pass None) comes from `_key_dates(_Net)` (only computed for full runs and its own drill-down): `_downstream(net, src, start, finish)` is a forward pass in dates from one activity alone (remaining durations on each calendar, lags on the lag-rule calendar). lags / fs_links carry `ladder_pairs` (SS + FF, same pair, same lag) and values without them. A full run saves a snapshot (`_hc_snapshot_save`, `<log dir>\health\<id>.json`: totals `HC_TOTALS`, per-check values, item keys per check) unless `save_snapshot=False`; `p6_health_check_compare` picks 'latest' / 'previous' among this database's snapshots of the project or any id, 'current' runs one. The full report must stay under 18,000 B (test). `p6_dangling` uses `_Net` (same definition as the dangling block) and `_dangling_suggest` (ladder: missing SS/FF with the same lag; else FS to/from the closest same-WBS activity by early dates).
- **Analysis** (`p6_health_check`, `p6_progress_check`, `p6_compare_projects`: read only, each from one `BEGIN` snapshot): open = not `TK_Complete` and not `SUMMARY_TYPES`; summary activities are no link end either (no logic, not in the relationship checks); DCMA relationship checks count the links whose successor is open. `_chk` decides pass on the unrounded pct or ratio and rounds only the reported values. `DCMA_CHECKS` (same order as the `DcmaCheck` Literal) gives each check its DCMA default, rule (`max` pct, `min` pct for fs_links, `ratio` value for cpli and bei; threshold None = report only) and its PROJPROP 'schedule_check' keys: `*_target`, `*_constraint` limits in hours, `check_*` = 'N' disables the check unless `thresholds=` names it (P6 spells `resouces_target`; `cpli_target` is always a % tolerance, 5 -> 0.95). `_dcma_settings` takes the project's schedule_check when stored, else the DCMA defaults (limits `DCMA_LIMIT_DAYS` = 44 d of each activity calendar, long lags in lag days from `_lag_hpd_sql`), then `thresholds=` (`ThresholdCheck` names: unknown ones and critical_path_test raise) and `high_float_days`; `threshold_source` says which. Logic exempts only the project start milestone (TT_Mile without predecessor, earliest start) from "no predecessor" and the finish milestone (TT_FinMile without successor, latest finish) from "no successor", and lists them; dangling starts and finishes (milestones left out: their one date is driven by any link type) are information only. Missed tasks and BEI match baseline activities by Activity ID through `_baseline_pid` (no baseline: not evaluated); due = baseline finish at or before the data date (datetimes), missed = not finished or finished on a later day (`date()`); `baseline_dates` (and the compare `dates`) 'current' = the baseline's `COALESCE(act_end_date, early_end_date)`, 'planned' = its `target_end_date`. CPLI = (data date to `scd_end_date` + `scd_end_date` to `plan_end_date`) / the first, in working days of the project calendar (`_Cal`), calendar days beside it. The critical path test is never run (no CPM engine). `p6_health_check` keeps the pre-DCMA top keys with their shapes and the values of the checks rules (`_dcma` returns `no_predecessor`/`no_successor` `{count, sample}`; `hard_constraints`, `high_float`, `negative_float` copy `{count, sample}` of their checks; `leads_negative_lag`, `positive_lags`, `non_fs_links` are counts of links whose successor is open). `p6_progress_check` counts `OOS_SQL` links (FS with lag >= 0, FS lead, SS, FF, SF) and status inconsistencies, and reports `sched_retained_logic`/`sched_progress_override` from `_sched_options`. `p6_compare_projects` joins `MAT_SQL` CTEs (an automatic index on task_code: a plain TASK-to-TASK join by task_code takes seconds) with a LEFT JOIN plus the reverse NOT EXISTS; links are keyed on `LINK_KEY` (pred code, succ code, type, pred project, NULL inside the project); variance is a `julianday` difference sorted on `ROUND(ABS(v), 6)` so float noise never reorders ties, and `variance_wd` uses the activity calendar per page row.
- **Network analysis** (`p6_driving_path`, `p6_float_origin`, `p6_redundant_links`, read only): `_Net(con, pid)` (via `_net_snapshot`, one read snapshot) loads the project's links (successor or predecessor in it), both activities (stored F9 dates of every status: P6 places completed ones too, retained logic), calendars, lag rule and `sched_lag_early_start_flag`. `gap(lk, late)`: anchor = predecessor date (`LINK_FROM`) plus lag on the lag-rule calendar (`lag_cal`; 24 h = timedelta; a negative lag uses `subtract_work_hours`), minus the part of a positive lag elapsed between the predecessor's actual start (SS, SF) or finish (FS, FF) and the data date when the flag is not 'N'; gap = working hours to the successor date (`LINK_TO`), on the successor calendar (early) or predecessor calendar (late). `GAP_TOL_H` (5 min) = zero. Oracle: every open activity of the reference project and of its XER import is explained on both passes. Roots: `_root_driver` (constraint `EARLY_CSTR`, data date, completed_predecessor, actual_date, open_start, unexplained); late sources: `cstr_hits(LATE_CSTR)` then `_late_origin` (plan_end_date must finish, open end, unexplained). `_transitive`: FS-only chains of 2 to `TRANSITIVE_DEPTH` links through non-summary activities, max lag sum per node (`best`, `best2` for 2 links or more), pruned past the latest target's early start.
- **CPM engine** (`_Cpm`, `p6_cpm_validate`, `p6_schedule_whatif`, `_cpt` for the DCMA critical path test; read only, never writes): `_Cpm(con, pid)` loads every activity, links inside the project (`ext_pred` / `ext_succ`: links to other projects with the other activity's stored dates), calendars and options; `copy()` for edits; `run()` -> {task_id: {es, ef, ls, lf, tf_h}}. Rules (oracle: the reference project and its XER: 100 % on open activities, early dates of completed ones): every status placed (retained logic); a completed activity sits at max(data date, predecessor bounds); between two completed activities the lag is ignored forward; `eff_lag` drops the lag elapsed between the predecessor's actual date and the data date (`sched_lag_early_start_flag` not 'N'), forward and backward; early start = `next_work_start`, late finish = `prev_work_end` (finish milestones too), durations via add/subtract_work_hours; open ends at the must finish date (`sched_use_project_end_date_for_float`); float per `sched_float_type` (FT_FF = finish float). LOE/WBS spans and ALAP are approximations; leveling, suspend/resume not modelled. `_cpm_compare` gives match rates (open: all five values; completed: early dates; completed late dates counted apart) and probable causes; `CPM_TRUST` 0.99 gates `_cpt` and the what-if `engine.trusted`. `_Cal.work_hours` uses a cumulative per-day index (`_cum`, rebuilt to cover both ends; exact against the day loop) so a pass takes about 0.5 s.
- **Activity codes**: `_code_type(con, pid, name)` resolves a type name (case ignored) as the project sees it: its own AS_Project type, else a type of its nearest EPS node (`_eps_chain`, PROJECT `proj_id` of the EPS), else a global one; the other types with that name are listed in `shadowed`, two at the best rank raise. `_code_tree` gives each code `chain` (ids from the top, cycle guard), `level`, `path` (short names joined with PREFER `name_sep_char`, else '.') and P6 `sort` (seq_num then id per level). `_code_filter(con, pid, code_type, code_value, include_children)` returns `(sql, args, info)`: an `EXISTS` on TASKACTV, any value without `code_value`, else the codes whose path, else short name, else name match (every match: 'MEC' finds CON.MEC and COM.MEC) plus their descendants unless `include_child_codes=False`; `code_filter` (matched, children, codes) tells what was used. `p6_query_activities`, `p6_lookahead` and `p6_float_analysis` take it.
- **Reporting** (read only, one `BEGIN` snapshot each; values of the last F9): `p6_group_summary` groups `_act_agg_sql` plus a critical count (`_critical_clause` of the project, open, `SUMMARY_TYPES` left out) by status (P6 order), task type, the WBS ancestor at `wbs_level` (`_wbs_tree`; a shallower node keeps its own) or the code ancestor at `code_level` ('(none)' last), merges with `_merge_agg`, pages with `_slice`; `totals` covers every grouped activity. `p6_lookahead`: half-open window `[from, to)` of calendar days from the data date (or `from_date`, 00:00 for a date alone), categories in_progress, starting, finishing, spanning, completed on remaining (else early) dates, computed as `w_*` SQL flags on a derived table over `_act_from` (the bounds are `_fmt_dt` literals) so rows and `counts` agree; `include_in_progress=False` still lists in-progress activities finishing in the window. `p6_progress_curve`: `_measure_rows` (units = labor and nonlabor assignments, cost = every assignment, `resource=` one resource) feed `_curve_items` (planned on the target dates, actual on the actual dates clipped at the data date, remaining from the remaining start but not before the data date; `earned` = target x `_perf_pct`, the activity % complete by `complete_pct_type`: CP_Phys physical %, CP_Drtn (original - remaining) / original duration, CP_Units actual / at completion units, i.e. P6 earned value with EC_Cmp_pct; never the actual quantity), spread by `_cum` (linear over calendar time with bisect; a zero-length item counts after its start; `_value_at` = the value at one instant) over `_period_edges` (months, or weeks from PREFER `week_start_day_num`, 1 = Sunday; more than `MAX_ROWS` periods raise). It is an approximation (P6 spreads over working time and curves, and TRSRCFIN/TASKFIN period actuals are not used): only values at the data date are exact, and the note says so. Earned value has no history in the database: it is given at the data date (`to_date`: spi = earned / baseline planned, spi_actual = actual quantity / baseline planned, variance = earned - baseline planned) and per update (`earned_points`), never as a period curve; curve percentages are of the budget. `checks.wbs_other_ev_technique` counts PROJWBS nodes whose `ev_compute_type` is not EC_Cmp_pct (noted, not applied). `p6_project_summary`: the primary % complete is units (actual / at completion, labor plus nonlabor, as `_rollup`; the S-curve percentages are of the budget), with physical % weighted by budget units, duration % and `units_vs_physical_mismatch` (activities with units whose physical % and 100 x actual / at completion units differ by more than 0.01 point) beside it; `spi_units` = earned units of `_curve_items` / `_value_at` of the baseline assignments at the data date; `longest_path` is None when TASK has no `driving_path_flag`. `p6_float_analysis`: `_float_edges` (finite, increasing, 0 added and noted), `_float_labels` and `_float_bucket`, which compares hours with edge x hours per day and never rounds: below the first edge, `[a, b)` under 0, `= 0`, `(a, b]` over 0, above the last edge, so `all_ranges_covered` must hold; `tf_not_whole_days` counts total float hours that are not a multiple of the calendar's hours per day. `p6_resource_summary`: TASKRSRC per `rsrc_id` (quantities and costs as stored, not time-phased), labor and nonlabor rows first; `by_status` counts distinct activities (`COUNT(DISTINCT CASE ...)`), not assignments; `totals` from the same snapshot, with quantities of labor and nonlabor assignments only (`other_type_assignments` = the rest; material has its own unit) and costs of every assignment.
- **Shared helpers**: user dates go through `_parse_dt(value, field)` (YYYY-MM-DD, optional HH:MM[:SS], 'T' allowed, same as `DATETIME_PATTERN`); DB and XER dates are read with `_db_dt` and written with `_fmt_dt`. P6 text trees (`CALENDAR.clndr_data`, `PROJPROP` values such as 'scheduling' and 'schedule_check') are parsed with `_blob_text` + `_p6_tree`, searched with `_p6_find`, read per project with `_props` (None when absent, `error` set when unreadable). `_baseline_pid(con, pid, baseline)`: the Project ID given, else `PROJECT.sum_base_proj_id`, else None.
- **Calendars**: `_cal_parse(clndr_data)` (LRU cache, immutable tuples) reads the `DaysOfWeek` and `Exceptions` nodes: day '1' is Sunday (Python weekday = (n + 5) % 7), shift attributes `s`/`f` come in either order with 1 or 2 hour digits, `f|00:00` means 24:00, exception `d|<serial>` counts days from 1899-12-30, an exception without shifts is a non-work day and one with shifts replaces that day's hours. `_calendars(con)` / `_calendar(con, clndr_id)` resolve `base_clndr_id`: the base week only when the calendar has no `DaysOfWeek` node, base exceptions merged with the calendar's own dates winning (depth cap 10); an unreadable calendar has no working time, takes nothing from its base and keeps `.error`. `_Cal` gives `shifts`, `is_workday`, `day_hours`, `first_start`, `last_end`, `work_hours` (= `work_hours_between`), `work_days`, `count_workdays`, `add_work_hours`, `subtract_work_hours` (backward mirror: lands on a shift start), `is_work_time` (shift `[start, finish)`), `next_work_start`, `prev_work_end` (a shift start gives the previous finish) (oracles: P6's F9 early dates of the reference XER; early and late dates of the reference project, 100 %). Calendar arithmetic is for working-time questions only; hours to days stays `day_hr_cnt`, and `week_hr_cnt` is never used in arithmetic (it is stale on several calendars, reported as a warning).
- **Write path** (every write tool follows the same flow):
  1. `with _write_session(confirm) as (con, backup):` wraps `_open_for_write`, which, if confirming, refuses when `PM.exe` is running and takes a backup (`_backup`, SQLite backup API) before every write (`backup_scope` every_write; `session` = once per process, the v2 behaviour kept for P6_DB_PATH without a config file), unless `backup_before_write` is off; plain backups are pruned to `backup_retention`, then runs `BEGIN IMMEDIATE`. The context manager always rolls back and closes on exit, so raising or returning early never leaves the DB write-locked. All write code must run inside it.
  2. Perform the change inside the transaction and build a human-readable `plan`.
  3. `_commit(con, plan, confirm, projects=(...), log=[...])`: rolls back and returns a dry run when `confirm=False`, otherwise re-checks PM.exe and commits. `projects` are the proj_ids whose schedule the change invalidates (both sides of a link, the edited activity's project unless only its name or physical % changed, the target of an update import; the project of a schedule options write; not a new project, baseline, EPS or deleted project): a confirmed commit returns them as `stale_projects`. `log` = one edit log entry per changed item (`operation`, `proj_id`/`project`, `table`, `keys`, `before`, `after` as stored, `summary`; `_rel_log` builds a TASKPRED one); without it one entry summarises plan[0]. The commit appends them (`_log_write`) with ts, a commit id, `tool` (`_caller_tool`: the p6_* frame on the stack, None from tests), `backup` (`_last_backup`) and `stale` = {proj_id: last_schedule_date} of `projects`, and returns `edit_log`.
  Several items in one transaction: `_batch(con, items, apply_one)` runs each item in a SAVEPOINT (a ValueError rolls back that item alone and is reported), `_batch_commit(con, b, confirm, head, backup)` is all or nothing (any failed item: dry run `would_refuse`, confirm `applied False`) with one log entry per item.
  Stamp `update_date/update_user` (and `create_*` on insert) via `_stamp_cols`; `_now_str` mimics the date format already present in `TASK.update_date`.
- **Staleness and edit log**: `_schedule_state(con, pid)` returns `{data_date, last_schedule_date, stale, edited_since_last_schedule {at, change, writes, log_entries}, note}` (raises for an EPS node or a deleted project), from `_edit_state`: the log entries (`_log_entries`, this database's file name only, cached per file by mtime and size) whose `stale[pid]` equals the current `PROJECT.last_schedule_date` and that no restore undid (`_undone_fn`: made after the restored backup's time, before the restore); `writes` counts commit ids. It survives restarts and is shared by server processes. Never compare `update_date` (imports and the TASK/TASKPRED triggers rewrite it). Tests simulate a reschedule by writing `PROJECT.last_schedule_date`.
- **Backups**: `_backup(kind)` writes `<db stem>_<YYYYMMDD_HHMMSS>[_kind][_n].db` in `_backup_dir()` (never overwrites; `BACKUP_NAME` parses it, `_backup_taken_at`). `p6_restore_backup` validates the name (a bare file name in the folder), compares projects (`_projects_of`), and on confirm refuses while PM.exe runs, runs `PRAGMA quick_check`, takes a `pre_restore` backup, copies with the SQLite backup API, clears `_cols_cache`, resets `_backup_done` and logs a `restore_backup` entry with `backup_taken_at`.
- **Tool registration**: every tool is declared with `@_tool(read_only, destructive, idempotent)`, never `@mcp.tool()`; it fills `TOOL_HINTS` (also under the test stub) and passes MCP `ToolAnnotations` when mcp >= 1.8 is installed. Read tools use the defaults; tools with `confirm` are `read_only=False, destructive=True`; `p6_import_xer` is also `idempotent=False`; `p6_export_xer` is destructive (overwrites a file); `p6_backup_database` is neither destructive nor idempotent. The test checks that `TOOL_HINTS` equals the set of `p6_*` functions. Parameter types (`Status`, `RelType`, `Direction`, `CstrName`, `XerTable`, `Pct`, `ProjectId`...) are module-level aliases because the SDK evaluates the string annotations against module globals; `Field` falls back to a no-op without pydantic. Keep the runtime checks in the tools too: tests and internal calls bypass the SDK validation. `XER_TABLES` is derived from `XerTable`. `INSTRUCTIONS` (passed as `instructions=`) must stay ASCII and under 1 KB. `_tool` registers a `functools.wraps` wrapper with the SDK that re-raises any exception as `ToolError` (message kept; other than ValueError/RuntimeError it is prefixed with the type name): mcp 2.x shows clients only 'Error executing tool <name>' for any other exception. The module keeps the plain function, so direct calls and the test still see ValueError. Raise plain ValueError in tools; never import ToolError elsewhere. `SERVER_VERSION` is passed as `version=` when the SDK accepts it (serverInfo.version).
- **New IDs** must come from `_next_key` (reads and bumps `NEXTKEY`, never below `MAX(id)+1`). Do not use `MAX(id)+1` alone.
- **XER import/export** (`_XerImport`, `p6_import_xer`, `p6_export_xer`): XER escapes line breaks as `\x7f\x7f` and doubles `"`; dates have no seconds (`_xer_decode` / `_xer_encode`). `_xer_read_meta(path)` returns `(header, tables, meta)`: it skips a UTF-8 BOM, decodes UTF-8 else cp1252 (`utf8_error_at` = file offset of the first bad byte), adds a repeated `%T` block to its table, skips `%R` lines before their `%F`, counts rows whose value count differs from the field count (padded or cut) and records `%E`; `_xer_read` is the 2-tuple wrapper. Import remaps every id through `idmap[table][xer_id]`; `XER_FK` lists the id columns carried by the XER, any other `*_id` is cleared. Global tables are matched by name (`match_or_create`; the global keys and queries live in `XER_MATCH`, shared with the pre-flight preview), project data per mode (`new`, `baseline` with `orig_proj_id`, `update`). A dry run performs the whole import and rolls back. P6 standalone keeps schedule options in PROJPROP 'scheduling' (no SCHEDOPTIONS table): `import_schedule_options` (default True for new and update, False for baseline) writes the XER SCHEDOPTIONS there through `_sched_write` with `imp.idmap['TASK']` as key activity map; when off, the warnings list the XER options that differ (`_sched_diff`). `p6_schedule_options` shows DB vs XER read-only. `create_eps` (`NewEps` TypedDict, mode new) creates or reuses the EPS node through `_create_eps` in the same transaction; with no EPS node and no create_eps the dry run sets would_refuse and confirm raises before the lock.
- **Import guards**: `p6_import_xer` runs `_xer_preflight(header, x, meta, xer_project, con)` (also served read-only by `p6_inspect_xer`) and, in update mode, compares `PROJECT.last_recalc_date` with the XER data date, on a read-only connection **before** `_write_session` (where `_import_target` also refuses an EPS node as the update or baseline target): pre-flight errors (no project WBS node, activity without WBS or calendar, duplicate Activity ID, assignment of an activity not in the file, field-count mismatch in an imported table) or an older XER data date without `allow_older_data_date=True` make `confirm=True` raise with no backup and no lock; the dry run still imports everything and sets `would_refuse`/`refuse_reasons` (without a project WBS node it imports nothing and returns that result with empty counts). The plan always has a `Data date:` line and the result carries `data_date {database, xer, older}` and `preflight`. Update mode records the TASKPRED/TASKRSRC ids it matched or inserted in `imp.touched` and `_missing_rows` reports the project's activities, links (both ends in the project; cross-project links are never touched) and assignments missing from the XER (`missing_from_xer`: count, by_type, 15 samples, `on_missing_activities`). Nothing is deleted unless `remove_missing` lists `TASKPRED`/`TASKRSRC` (`_remove_rows` deletes by id; an assignment's UDFVALUE, TRSRCFIN, RSRCHOUR and ASGNMNTACAT rows first; counted as `counts[T]['deleted']`); `'TASK'` raises: activities are never deleted, and rows of a missing activity are never removed. TASKRSRC rows of an unmapped activity are `skipped_unmapped`. The Project ID limit is `PREFER.proj_short_len` (`_prefer`), else 40.
- **Activity edits** (`p6_update_activity`): user dates go through `_parse_dt` before the write session (a malformed date takes no lock), then `_resolve_dt(cal, value, field, edge)` with the activity calendar: an explicit time is kept (noted on a non-work day: real data has actuals at any time and on non-work days), a date alone takes the first shift start (actual start, start constraints) or the last shift end (actual finish, `CSTR_FINISH` constraints; 24:00 = next day 00:00) and is refused on a non-work day; without a readable calendar a date alone starts at 08:00 and a finish needs a time. A milestone (`TT_Mile`, `TT_FinMile`) has one date: either actual date is resolved with the start (`TT_Mile`) or finish (`TT_FinMile`) edge, written to both `act_start_date` and `act_end_date` (P6 stores AS = AF) and completes it; two different dates are refused. Durations finite and >= 0, `physical_pct` 0 to 100, actual finish not before actual start (compared as datetimes), actual dates after `PROJECT.last_recalc_date` only with `allow_after_data_date=True`; notes (pct 100 without an actual finish, resolved times) are plan lines.
- **EPS**: an EPS node is a `PROJECT` row with `project_flag='N'` plus one `PROJWBS` row with `proj_node_flag='Y'`; a project's node `parent_wbs_id` points to its EPS node. Baselines are `PROJECT` rows with `orig_proj_id` set; `p6_list_projects` hides both by default.
- **PROJPROP writes** (`p6_set_schedule_options`, import): `_p6_tree(text, strict=True)` (a repeated key in a node raises) and `_p6_dump` round-trip the stored text byte for byte (node `num` kept); `_set_props(con, pid, prop, values, lpl, now)` keeps key order, unknown keys and nodes, appends new keys in spec order, keeps a BLOB row a BLOB (new rows are TEXT, as P6 writes them), writes nothing when the text is unchanged, and restores a soft-deleted row. `SCHED_SPEC` / `CHECK_SPEC` (`PROP_SPEC`) give kind and P6 default per key in P6's order; `_norm_opt` validates and formats (flag Y/N, int, `float` as repr: 25.0, `num` int when whole, allowed-value tuples; `lenient` keeps an unknown XER token with a warning). The key activity is a task_id (`_key_task` from an Activity ID, `_xer_sched_values` maps the XER id, -99 + warning when unmatched). Level priority list: `(0||field(sort_type|ASC)())` children of LevelPriorityList, shown as 'field:ORDER' (`_lpl_of`, `_lpl_text`, `_xer_lpl` for the XER 'field,ASC_BY_FIELD/ASC'). `_sched_diff` compares the level priority list when both sides read, and an XER key activity id the XER does not contain equals none. The enum tokens rcal_ProjDefault and SD_None are not confirmed by a P6 export yet.
- **Project delete** (`p6_delete_project`): measured against a P6 GUI delete (a backup vs the DB after): hard delete, P6's AFTER DELETE triggers fill REFRDEL, no soft delete, NEXTKEY untouched, order `DEL_ORDER`. `_del_sets` builds temp id sets (`_dp`, `_dt`, `_dw`, `_dr`, `_dct`), `_delete_rows` deletes from every `_db_tables` table through `DEL_OWN` columns (and UDFVALUE by `DEL_UDF`), counting rows of other projects (`foreign`, refused except TASKPRED). `DEL_CLEAR` columns of remaining rows are set NULL. `_orphans` (ORPHAN_REFS + UDFVALUE fk per UDFTYPE.table_name) runs before and after inside the transaction; new orphans refuse the confirm. The dry run really deletes, then rolls back. 
- **Deliberate non-features**: the edit tools never write planned/early/late dates or float (P6 recomputes them on F9; tell the user to open P6 and press F9 after writes). Activities are only created by XER import. `p6_delete_activity` hard-deletes one activity (`_act_delete_rows`: every `_db_tables` table through `ACT_DEL_OWN` columns task_id, pred_task_id, taskrsrc_id, UDFVALUE of TASK and TASKRSRC, DISCUSSION_READ of its discussions; `ACT_DEL_CLEAR` rows (PROJISSU.task_id) kept with the link cleared; rows still naming it afterwards refuse), refuses actual dates without `force=True` before the write session (the dry run sets `would_refuse`), logs the activity snapshot and its links, and marks its project and the neighbours' projects stale.
